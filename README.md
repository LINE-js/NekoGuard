# NekoGuard

[LINE.js](https://github.com/JS-PACKAGE/LINE.js) 的獨立 Node.js／TypeScript 反詐騙外掛，使用 `/api/ws` 的 `scam:check` 呼叫既有 Jev 系統。詐騙機率達到 `config.yaml` 的門檻（預設 **≥ 70%**）時，重新取得社群當下管理員／共同管理員，在原聊天室回覆來源訊息並真正 @ 提及所有查得的管理員，附上機率、疑似手法與手法信心度。

自己的訊息在付費分析前排除，包含同帳號手機訊息及外掛警示。OpenChat 的 `p…` 成員 ID 與一般帳號的 `u…` ID 分別比對；不能取得自身社群身分時，不猜測、不呼叫 Jev。

## 安裝

需要 Node.js ≥ 22、npm，以及已登入的 LINE.js。**先用次要 LINE 帳號驗證**；此服務使用非官方 LINE API，可能觸發帳號風控。

### 1. 套用 LINE.js 後端擴充

上游原有 API 無法列出完整管理員，也不允許標記尚未發言的人，因此本專案附帶必要補丁：

- `integrations/linejs-admins.patch`：後端實作、回歸測試與上游說明更新。
- `integrations/linejs-base.json`：基準是 LINE.js **1.6.5**，commit [`8f1e4813dd69593fec06924744913ea1f7b224f3`](https://github.com/JS-PACKAGE/LINE.js/tree/8f1e4813dd69593fec06924744913ea1f7b224f3)。

在 NekoGuard 目錄執行：

```sh
npm ci
npm run build
npm run patch:linejs -- /path/to/LINE.js
```

安裝器先核對 commit 並執行 `git apply --check`；版本不同、已套用或有衝突會拒絕，不會自動切換版本、丟棄本機修改或重新啟動服務。若現有 LINE.js 版本不同，請準備基準 commit 的獨立工作副本，不要強制覆蓋既有環境。補丁修改來自 Apache-2.0 授權的 LINE.js 專案；上游的授權檔案保持不變。

套用後，在 **LINE.js 目錄**執行 `npm ci`、`npm run build`，並於完成下一步設定後重新啟動 LINE.js。這是本機補丁；升級上游前需重新檢查相容性，不能假設更新後仍保留擴充。

**已套用舊版擴充者**：本版補丁包含管理員授權、資料傳輸及伺服器限流修正；只更新 NekoGuard 程式不會更新既有 LINE.js 後端。請在基準 commit 的乾淨獨立副本套用目前補丁、驗證並重新建置，再自行安排切換；不要強制覆蓋既有設定或未提交修改。

### 2. 設定 LINE.js

在 **LINE.js 自己的 `config.yaml`** 合併下列區段，不要覆蓋其他設定：

```yaml
api:
  enabled: true
  chats:
    - m0123456789abcdef0123456789abcdef # 換成要監測的社群聊天室 ID
  sendsPerMinute: 20
jev:
  token: '' # 在 LINE.js 本機填入 TypeSafe API key
  model: jev-1.13.0
```

重新啟動 LINE.js，確認已登入，再於該目錄執行 `npm run cli -- token` 產生機器人 Token。Token 只顯示一次，請勿貼到日誌、版本控制或聊天。

**兩種金鑰不同**：TypeSafe key 只放 LINE.js；NekoGuard 使用 LINE.js 產生的機器人 Token，不讀取 `session.json`，不自行登入 LINE。

### 3. 設定並啟動 NekoGuard

本機已有 `config.yaml`；若是從版本控制取得的新副本，先將 `config.example.yaml` 複製成 `config.yaml`（不要覆蓋既有檔案）。

```yaml
api:
  url: ws://127.0.0.1:3789/api/ws
  token: '' # 填入 LINE.js 機器人 Token
detection:
  thresholdPercent: 70
```

`NEKOGUARD_API_TOKEN` 環境變數可覆蓋 `api.token`；空 Token 會拒絕啟動。`config.yaml` 已列入 `.gitignore`，請保持權限 `600`。遠端連線必須使用 `wss://`，只有本機回送位址允許 `ws://`；URL 不得夾帶金鑰、query 或 fragment。

```sh
./start.sh
# 或使用另一份設定（相對路徑以 NekoGuard 目錄為基準）
./start.sh --config /path/to/config.yaml
```

`start.sh` 會檢查 Node.js ≥ 22 與 npm，每次依 lockfile 安裝依賴（含編譯需要的 devDependencies）、編譯，再啟動程序；任一步失敗就停止。可從其他目錄呼叫，不會建立或覆蓋 `config.yaml`，也不會自動安裝 Node.js、套用 LINE.js 補丁或啟動 LINE.js。已安裝及編譯完成時，也可用 `npm start` 直接啟動。

設定修改後重新啟動外掛。看見 `MONITORING_READY` 表示 LINE 已登入且後端支援管理員擴充；`SCAM_ALERT_SENT probability=70% admins=20/21` 表示一批通知已由 LINE.js 確認送出（不是管理員已讀）。`SIGINT`／`SIGTERM` 可停止程序。

## 行為與限制

- **範圍**：監測 `api.chats` 內的 OpenChat（`square`）即時文字與文字編輯。一般群組、多人聊天室、私聊沒有此套 OpenChat 管理員角色，因此不監測；不拿全體成員或曾發言的管理員冒充完整名單。
- **門檻**：`probability >= thresholdPercent / 100`，不先四捨五入；70% 含等號。`tactic.confidence` 是手法分類信心，不是詐騙判定門檻。缺少手法時明確顯示未提供，不自行編造。
- **通知**：在原聊天室回覆來源訊息，每則最多標記 20 人、UTF-16 範圍符合上游限制。可標記未發言管理員；後端僅授權同一連線、同一聊天室最後發起且成功完成的查詢。新查詢立即撤銷舊名單與未完成舊查詢的授權資格；舊成功結果回 `CHAT_ADMINS_FAILED`，不因新查詢等待、成功或失敗而恢復舊授權。登出同樣撤銷授權。沒有管理員或查詢失敗時記錄錯誤，不改標記全體成員。
- **通知格式化**：共用固定 `zh-TW` 百分比格式器，避免每次產生通知時重建 locale 格式化設定。管理員名稱逐字清洗並截斷至 80 個 UTF-16 單位，不切斷有效 surrogate pair、不先產生完整清洗副本；達到顯示上限後不掃描其餘後綴。原有空白折疊與先 trim 後截斷語意不變；未達上限的全空白或長空白尾端仍需掃描。輸出精度、分批內容與提及位置不變，格式化不參與門檻判定。
- **訊息排除**：自己的訊息、歷史 snapshot、已收回、無法解密、系統事件、圖片／其他非文字都不分析。自己在手機發出的社群訊息亦排除，不會讓警示形成分析迴圈。
- **重複與競態**：記住最近 5000 則訊息版本，只保留必要識別碼、內容雜湊與版本狀態；工作佇列及去重紀錄不保留訊息原文、發送者名稱或完整 API payload。相同內容不重複分析，修改後重新判定。編輯時先作廢舊結果與待發通知，再判斷新版能否入列；即使分析佇列滿載，也不會送出舊版本警示。編輯、收回、登出或停止會取消失效工作的本地限流等待，釋放工作名額，但不重設全域限流。已送出的 API 請求仍等待回覆或逾時，不假設已取消、不自動重送；已送出的警示不自動收回。
- **訊息指紋**：使用 Node 22 支援的 [`crypto.hash`](https://nodejs.org/docs/latest-v22.x/api/crypto.html#cryptohashalgorithm-data-outputencoding) 一次性計算 SHA-256，避免每則訊息建立串流雜湊物件；維持原本 UTF-8 輸入、hex 輸出及去重規則，不新增依賴。
- **聊天室移除**：聊天室從 `channels` 清單移除（或不再是 `square`）時，永久作廢該聊天室的舊工作、清除自己的社群身分快取並取消本地等待，不影響其他聊天室。重新加入不恢復舊分析或待發通知；新訊息會重新確認身分。已送出的請求仍受原並行與串行限制追蹤至結束，遲到回覆不能恢復舊身分或警示。
- **低延遲排程**：分析與通知使用獨立的有界排程，各最多同時處理 4 個工作；通知等待送出或確認時不占用分析名額。結果可能不按訊息順序送達。首次分析仍先確認自己的社群身分；同聊天室只有一個工作進行首次查詢，其餘留在有界分析佇列，成功後共用身分資料，不會因同一查詢占滿分析名額。管理員查詢與整批通知只在同一聊天室內串行，避免撤銷尚在使用的標記授權，不同聊天室可獨立進行。同聊天室的待發通知不占用其他聊天室的通知名額。所有聊天室仍共用全域分析、管理員查詢及發送間隔；這不會降低 Jev 推論時間或增加上游額度，不需更新 LINE.js 補丁。
- **API 傳輸**：沿用 JSON／WebSocket 協定，以連線內遞增的 base-36 短 ID 取代 UUID，減少每筆請求及回覆的 `requestId` 大小，亦省去 UUID 產生。使用 BigInt 避免數值精度造成重複 ID；逾時後不重用 ID，遲到回覆不會誤配新請求。Bearer 認證、分析／通知額度及不自動重送的規則不變，不需更新 LINE.js 補丁。
- **輸入解析**：訊息的 `channelKind` 必須是協定允許的字串，不對陣列或物件做字串強制轉型；畸形值會被忽略，不會因轉型例外中斷接收事件。
- **請求資源**：API client 先完成 JSON 序列化，再建立 pending Promise 與逾時計時器；循環參照、BigInt 或拋錯 getter 等無法序列化的欄位會以 `INVALID_REQUEST` 拒絕，不傳送、不保留懸掛請求，也不洩漏原始欄位錯誤內容。
- **頻率**：沿用上游所有機器人合計每分鐘 10 次 Jev 分析；管理員查詢亦合計每分鐘 10 次，分別以至少 6.1 秒間隔排程。通知至少間隔 3.1 秒，配合預設每分鐘 20 則上限。三類間隔均以單調時鐘計算，不因系統時間快轉而跳過限流，也不因時間回撥而額外停等。多個機器人或較低的伺服器發送上限仍可能收到 `RATE_LIMITED`。建議一個 NekoGuard 實例，不要為提高流量而繞過上游限額。
- **繁忙與斷線**：待分析與待通知佇列各最多 500 則（不含各自執行中的工作）。分析佇列滿載時記錄 `ANALYSIS_QUEUE_FULL` 並略過新項目。通知先啟動較早且可執行的排隊工作；若仍有空閒名額且該聊天室沒有執行中的通知，新結果可直接執行，不占等待佇列容量。只有必須等待且佇列已滿時，才記錄 `NOTIFICATION_QUEUE_FULL` 並略過該次通知，不重試；並行上限與全域限流不變。等待過久、訊息被上游快取淘汰也可能分析失敗。首次連線失敗、WS 斷線或 hello 逾時後，固定等待 10 秒再連線，失敗無限重試；同時只安排一次重連。斷線時作廢舊佇列與通知，不補抓離線歷史或重送未確認的通知。`Ctrl+C`／`SIGTERM` 會取消重連並退出。設定錯誤、缺少必要擴充等非連線致命錯誤仍退出；修改設定或 Token 後需重啟。不保證高流量或離線期間的完整涵蓋。
- **失敗處理**：請求逾時、限流或發送失敗不會自動重試，避免付費重複分析或不確定是否已送出的重複通知；部分批次成功會留下已通知人數紀錄。無法分析不代表安全。
- **資料與費用**：外掛不保存聊天內容或登入 session 到磁碟。自動分析會將別人的文字透過 LINE.js 送至 TypeSafe，依其方案計費；請先告知社群並確認資料處理政策。模型結果只供查證，不是事實判定，不會自動刪訊息、踢人或封鎖。
- **名單一致性**：每次通知前重新完整分頁查詢目前成員，不使用 senderRole 快取；LINE 沒有跨頁原子快照，查詢／發送期間的人員異動仍可能競態。任何頁面失敗或缺漏都不回部分名單。

## 驗證

```sh
npm test
npm run typecheck
npm audit --audit-level=high
```

已在 Node.js 26.7.0 執行：

- 外掛建置與 44 項行為測試通過，涵蓋跨聊天室隔離、聊天室移除／重新加入永久作廢舊工作與刷新身分、滿載時利用空閒通知名額且維持容量上限、分析／通知獨立並行上限、通知佇列回收、分析佇列滿載時編輯仍作廢舊分析與待發通知、首次查詢共用且不放棄已送出請求、失效工作立即取消本地等待、帳號切換作廢通知、發送失敗釋放通道、跨聊天室全域限流、系統校時不跳過或延長三類 API 間隔、短 ID 的亂序回覆與逾時隔離、序列化失敗不傳送且不留下懸掛請求，以及訊息種類不接受強制轉型。已移除只鎖定通知措辭的測試，保留數值、提及、分批、名稱空白／UTF-16 截斷邊界與敏感內容排除驗證。先前 npm audit 無已知漏洞。
- 補丁後 LINE.js 前後端型別檢查、建置與 240 項測試通過，含管理員授權邊界、分析前本地預檢、等待期間訊息變更，以及身分共用查詢的跨聊天室／登入隔離、失敗回收與明確管理員查詢維持獨立。另涵蓋系統校時下的配額與快取有效期邊界，以及歷史訊息時間更新後的排序、分頁與游標邊界。
- 補丁安裝器已在乾淨的基準副本實際套用成功。
- 隔離 smoke：實際啟動 `dist/main.js`，經 Bearer 認證的真實 WebSocket／LINE.js hub，使用實際 Jev 回應解析、Provider 分頁及發送 metadata 組裝；確認 69.999% 不通知、70% 分兩批標記 21 位最新管理員（含未發言者），自己的手機訊息與警示回流不送分析。
- 並行排程 smoke：啟動真實 `dist/main.js` 連接本機受控 WebSocket 服務，維持預設限流；第一則 Jev 結果刻意暫不回覆，第二則仍於下一額度開始並完成 90% 管理員通知，兩次分析實測間隔 6103 ms；自身訊息沒有送入分析。此項不連接真實 LINE／TypeSafe。
- API 傳輸 smoke：使用同一組 120 筆管理員查詢、分析及通知請求，實際連接本機 WebSocket，比較優化前後雙向傳輸量。JSON payload 減少 21.2%；含 WebSocket framing 的資料量減少 20.7%（不含握手、TCP/IP 或 TLS overhead）。此為固定小訊息樣本，不代表所有流量或 Jev 推論延遲均有同等改善。
- 排程與記憶體 smoke：實際 `ApiClient`／`ScamGuard` 連接本機 WebSocket，以加速間隔對照相同場景。A 聊天室通知未確認時，B 仍完成身分查詢、分析並送出通知請求；前四則等待通知時，第五則分析仍完成。處理 5000 則各 4 KiB 原文後，去重紀錄保留的原文字節由 20,480,000 降為 0（不是整體 heap 用量，也不代表不暫時解析輸入原文）。外部回應為受控 fixture，未連接真實 LINE／TypeSafe。
- 邊界修正 smoke：實際 `ApiClient`／`ScamGuard` 經本機 WebSocket 重跑已重現的三個案例：500 筆分析佇列滿載後編輯正在分析的訊息，不再送出舊版本警示；A 的四則訊息等待一筆首次身分查詢時，B 仍完成身分查詢與分析；四個限流等待中的工作收回後立即釋放名額，B 可開始身分查詢，但分析仍等原額度到期。限流使用加速設定，回應受控，未連接 LINE／TypeSafe。
- 聊天室生命週期與通知容量 smoke：實際 `ApiClient`／`ScamGuard` 經本機 WebSocket 確認聊天室移除再加入後，舊分析不再發出警示；A 有 500 筆待發通知且發送尚未確認時，B 仍能使用空閒名額送出通知，等待佇列保持 500 筆。使用加速排程與受控回應，這是壓力邊界驗證，不代表一般流量容易達到此容量；未連接 LINE／TypeSafe。
- API 請求資源 smoke：真實本機 WebSocket 下，循環參照請求修正前先拋 `TypeError`，隨後出現未處理的 `REQUEST_TIMEOUT`；修正後只拒絕 `INVALID_REQUEST`，等待超過原逾時後仍無未處理 rejection，後續有效請求正常完成，伺服器只收到有效請求。
- 通知格式化 smoke／量測：固定 21 位管理員，涵蓋 18 組機率與手法資料（含 0、1、負零、極小值及未知／缺省手法）；前後完整輸出雜湊一致。暖機後各執行五輪、每輪 5000 次 `buildAlerts`，本機中位耗時由 75.4 ms 降為 15.6 ms（約減少 79.3%）。這只量測文字產生的 CPU 耗時，不代表模型推論、LINE 發送或整體端到端延遲有相同比例改善。
- 輸入解析 smoke：`channelKind: ["square"]` 修正前錯誤通過型別檢查，`channelKind: {"toString":"square"}` 會拋 `TypeError`；修正後皆被拒絕。實際 `ApiClient`／`ScamGuard` 經本機 WebSocket 收到兩則畸形訊息後仍能分析下一則有效訊息，僅發出一筆管理員查詢與一筆分析請求；沒有連接 LINE／TypeSafe。
